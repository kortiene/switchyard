## Design Context

> Scope note: the primary frontend is **Switchyard Mission Control**
> (`crates/switchyard-ui/`), a native GPU-rendered Rust/Rune application over the
> Rust mission ledger. The optional **ADW Cockpit** Pi TUI extension
> (`.pi/extensions/adw-cockpit/index.ts`) remains the legacy reference for its
> visual language. There is no web stack, so web-specific layout and motion
> guidance does not apply wholesale; the transferable principles do: bold
> hierarchy, a dominant color with rare sharp accents, spatial rhythm,
> intentional structure, and a distinctive point of view that is not generic.

### Users
Developers/operators inspecting recoverable missions. They keep the dashboard
open while working and glance at it ambiently; mission navigation, ledger
health, and anything needing an operator must be visible before low-level
history. They drill down for hashes, commands, and copy-only CLI guidance. The
native dashboard is strictly read-only through `Host::inspect`; it never takes
the owner lock or owns git/forge. The legacy Cockpit observes the frozen ADW
state instead and is also read-only by default.

### Brand Personality
Instrument-grade · deliberate · operational. The literal product name is
"Cockpit", so the metaphor is a **mission-control dashboard**: every readout is
real signal, calm until something needs attention, confident rather than
decorative.

### Aesthetic Direction
A dark **mission-control dashboard** mapped to native Rune primitives (with a
light theme and the same visual language in the legacy terminal reference):
- **Numbered, titled, sharp-cornered panels**: `1. OVERVIEW`, `2. MISSION`,
  `3. ATTENTION`, then `4. PIPELINE`. Operator needs sit before lower-level
  limits, workspace details, history, and CLI guidance.
- **`key : value` rows** with a dim, padded key column against status-coloured
  mono values. Compact summaries stay dense; objectives, errors, guidance, and
  attention reasons wrap instead of being silently clipped.
- **Status dots + completion meters** distinguish done/current/pending/blocked
  states. A blocked step does not erase completed history, and an off-forward
  phase does not wear a healthy green meter.
- A heading pairs the last completed read with an explicit **not read / reading
  / polling / paused / read failed** state. Auto-refresh is not called `live`:
  connectivity and polling are different facts.
- **Responsive**: overview and mission panels sit side by side when wide and
  stack when narrow; the phase grid wraps, critical prose wraps, and usability
  is verified at the 760×520 minimum window.
- **Theme-native colour**: Rune `tok` theme/accent tokens for native surfaces,
  and the Pi theme API in the legacy extension. `success` means done/healthy,
  `warning` marks in-progress or incomplete states, and `error` marks alerts.
  Never introduce one-off hardcoded palettes.

### Design Principles
1. **Every glyph is signal.** No decoration that doesn't encode real run state.
2. **Bold via hierarchy, not noise.** Heavy header + dim labels + bold values;
   one highlighted current-phase chip, not a rainbow.
3. **Honest instrumentation.** Show all phases and read states truthfully;
   distinguish an unread, empty, in-flight, and failed ledger read rather than
   presenting them all as zero missions.
4. **Bolder, not bigger.** Keep selected-mission identity, phase, objective, and
   attention above the fold. Fold secondary revision/runner details into compact
   rows instead of expanding every panel equally.
5. **Theme-native and operable.** Colours/backgrounds degrade gracefully across
   dark/light native and terminal themes. Controls have descriptive accessible
   names, boundary states, visible focus/press feedback, and text alternatives
   to colour.
